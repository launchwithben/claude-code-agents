# AGENTS.md — installing claude-code-agents into a project

You are an agent asked to install this kit into the user's project. Read `README.md` for what each part does; this file is the procedure. Work from the target project's root; give absolute paths in anything you report. Prerequisites: `bash`, `python3` (hooks and installer, stdlib only), `git`, and `node` 18+ (the lead's ledger, the PM delta, the pulse script). If you have a local copy of this repo instead of network access, use it in place of the README's `git clone`. Nothing in the kit makes a network call or installs a package.

## What the kit is
A set of Claude Code subagents rendered from templates with the project's prefix: `lead` (the main-session seat, never a subagent), `pm`, `dev`, `ui`, `concept`, and any extra roles the overlay declares. Hooks: a handback check (a role cannot finish without the evidence its contract names), a territory guard (a file maps paths to owning roles) or, without a territory file, a regex routing guard, a role picker, and the lead's in-flight recorder and heartbeat. `install.sh` installs it from the project's **overlay**, `roles.config.json`; `install.sh --check` reports drift; `kit-check` runs every fixture.

## Procedure
1. **Detect, do not assume.** Find the project's real check command (`package.json` scripts, `Makefile`, CI config, `AGENTS.md`/`CLAUDE.md`). Check whether `.claude/` exists and is gitignored, and whether `.claude/settings.json` already has hooks. If there is no check command, say so and ask the user which command proves a change works. Never invent one.
2. **Get the kit at a tag** next to the project, not inside it: `git clone --branch v0.2.3 https://github.com/launchwithben/claude-code-agents ../claude-code-agents`. (This file is read from that clone or from GitHub; the clone is what the next steps run.)
3. **Write the overlay.** `bash ../claude-code-agents/install.sh --init` writes a starter `roles.config.json`; set `prefix` (a short project word), `gate` (the real check command from step 1) and `kit` (the version you cloned). Drop roles the project does not need from `roles` (a project with no UI does not need `ui` or `concept`; say you did). Only add a `territory` file if the user wants ownership enforced and can say which paths belong to which role: its path goes in the overlay, its format is in the README. Do not invent PM board rules; leave `pm` as the user states it. **`--init` writes a populated EXAMPLE, not a blank**: `prefix` is `acme`, `pm.repo` is `acme/widgets`, `extraGates` names a script that does not exist, and `territory`, `skills`, `chains` and an example `docs` role are included. Trim `roles` to what the project uses, and delete every key that does not apply (a project with no UI drops `ui` and `concept`; one with no board drops `pm`). `install.sh` prints a WARNING for example values it can see; do not ignore one.
4. **Install:** `bash ../claude-code-agents/install.sh`. It merges (never overwrites) `.claude/settings.json`: it refuses a file it cannot parse and writes nothing in that case. Do not hand-edit the installed hooks or agents.
5. **Fill in the rules skills.** `<prefix>-build-rules` (and `<prefix>-design-rules` if there is a UI) are starters written once. Fill them from the project's own docs, under about 900 words, citing only files that exist; or, better (this needs `roles/skills.txt`, which you create by hand; if the project has no written rules, keep a thin start and delete the "skills" key), list the doc sections in `roles/skills.txt` so `build_skills.sh` generates them and `--check` catches drift. If the project has no written rules at all, keep only the check command and say the file is a thin start.
6. **Prove it:** `bash scripts/roles-kit/bin/kit-check` must end with `ALL <n> FIXTURE FILES PASS`; `bash ../claude-code-agents/install.sh --check` must say `clean`.
7. **Wire the gate.** Add `bash scripts/roles-kit/bin/kit-check` (and `bash scripts/roles-kit/bin/build_skills.sh --check` if the project uses generated skills) to the project's own check command, or tell the user to; the installer prints the lines. The `install.sh --check` line it prints runs from the kit clone, so it only belongs in a gate where that sibling clone exists (not in most CI); leave it out otherwise.
8. If `.claude/` is gitignored, tell the user the roles must be committed with `git add -f .claude/ scripts/roles-kit roles.config.json` or a fresh worktree will not have them; add `tmp/` to `.gitignore`. Do not change `.gitignore` yourself.
9. **Report to the user what you cannot do**: (a) restart Claude Code if `.claude/agents/` did not exist when the session started; (b) accept the workspace trust prompt, because hooks in agent files run only in a trusted folder; (c) hooks defined in agent files do not fire under `claude -p`; (d) how to start the lead: `claude --agent <prefix>-lead`.

## Rules
- Do not edit installed core files (`scripts/roles-kit/`, `.claude/agents/<prefix>-*.md`): the next install overwrites them and `--check` calls the edit DRIFT. Change the overlay instead.
- Do not rename role suffixes in the overlay's `handback` keys without matching agent names: the contract is selected by suffix or full name.
- Do not commit, push or change git config. Leave the install as uncommitted changes for the user to review.
- The handback check reads what a role reports, not what it ran. State that limit if the user asks what the hook guarantees.

## Maintaining this repo (for agents working on it)
- Run `bash kit-check` before every commit; it must print `GREEN`. Every hook or script change needs a fixture, and every fixture file starts by parsing the script it tests (a bash syntax error exits 2 = block).
- Every change that alters behaviour gets a `CHANGELOG.md` entry and, when it ships, a `VERSION` bump and a release tag. How a fix found in a consuming project flows back: `MAINTENANCE.md`.
- Nothing project-specific enters this repo: no client names, absolute paths, board ids or product rules, in code, fixtures or docs. Those are overlay config.
- Keep the status line at the top of `README.md` and `MAINTENANCE.md` true. If the project is being sunset, follow the four steps in `MAINTENANCE.md` in order and do not archive the repo without the owner's say-so.
- Never add telemetry, dependencies or new network calls. The README promises there is no telemetry and nothing is sent anywhere; the only network use is the PM delta calling the user's own `gh`.
